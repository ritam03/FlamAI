# Part C — Decision Memo: Casualizing Indic-Language Outputs

## Recommendation: (a) SFT on synthetic "casualized" pairs, with a Day-1 prompt-engineering baseline

### Assumptions

1. The main model (FLM-4B-Instruct) already produces grammatically correct Indic outputs — the problem is register/tone, not fluency.
2. "Casual" is definable: shorter sentences, colloquial particles (Hindi: ना, यार, बस; Kannada: ಅಲ್ವಾ, ಮಾರಾಯ), contractions, reduced honorifics. Not slang-heavy or code-mixed (unless specified).
3. Synthetic "casualized" pairs can be generated by prompting a strong model (the main model itself, or an external model during data prep only — no API budget needed at inference time since we use the A100 for generation).
4. The LoRA adapter for a 4B model fits comfortably within A100-80GB alongside the base model.

### Back-of-Envelope Arithmetic

**Data volume:**
- Target: 5,000 formal→casual pairs per language × 6 languages = 30,000 pairs total
- Generation: Using FLM-4B on the A100 at ~200 tok/s goodput (from Part B), each pair ≈ 150 output tokens → 30K pairs × 150 tok = 4.5M tokens → 4.5M / 200 = ~6.25 hours of GPU time for synthetic data generation
- Quality filtering + dedup: assume 70% pass rate → need to generate ~43K raw pairs → ~9 hours GPU time

**Training cost:**
- LoRA fine-tune on 30K examples: ~2,000 steps at batch 16, each step ≈ 0.5s on A100 → ~17 minutes. Even full fine-tune would be < 1 day. Cost is negligible.
- Total GPU time for data gen + training: < 12 hours out of 336 GPU-hours available (2 weeks). Leaves ample room for iteration.

**Reviewer throughput:**
- 10 h/week × 3 weeks = 30 hours total
- At ~2 min per pair (read formal + casual, rate 👍/👎): 30 pairs/hour → 900 pairs total
- Reviewer covers Hindi + Kannada only → 450 validated pairs per language
- Strategy: validate 450 Hindi pairs → use validated patterns to template the other 4 languages. Validate 450 Kannada (Dravidian control) to check cross-script transfer.

**Why not (b) inference-time rewriter:**
- Adds 50–100ms latency per response (unacceptable for conversational UX)
- Still needs training data (same data problem, plus a second model to maintain)
- Doubles serving cost per Indic request — contradicts the cost concerns from Part A

**Why not (c) prompt-only:**
- Prompt engineering burns tokens on every request (permanent per-request cost increase)
- Prompt instructions are brittle across 6 languages — what works for Hindi won't for Tamil
- Doesn't scale: each language needs a different prompt, and prompts can't carry enough examples for consistent style

### Success Metric

**Primary:** On a held-out set of 100 formal→casual pairs per language (reviewer-evaluated for Hindi/Kannada, model-judge proxy for the other 4):

> **≥ 70% of SFT outputs rated "appropriately casual" by the reviewer** (Hindi/Kannada), with no increase in factual error rate.

**Secondary:** Token count per response does not increase by > 15% (casual shouldn't mean verbose).

### Kill Criterion

**By end of Week 1:** Run a pilot SFT on Hindi-only (5K pairs, LoRA). If:

> Reviewer rates < 50% of pilot outputs as "appropriately casual" on a 100-sample blind A/B test (SFT vs base model), **abandon SFT** and pivot to (b) with the validated data as rewriter training set.

Rationale: if the model can't learn register shift from 5K Hindi examples, more data or more languages won't help — the problem is likely in the model's Indic representation, and a specialized rewriter is the fallback.

### Day-1 Experiment

1. **Morning (2h):** Craft 5 prompt-engineering templates for Hindi casualization. Run on 50 held-out formal Hindi responses. Have the reviewer score them over lunch. This establishes the **prompt-only baseline** (expected: ~30-40% "casual enough").

2. **Afternoon (3h):** Generate 5K synthetic Hindi formal→casual pairs using the main model with a carefully crafted "casualize this" prompt. Apply basic quality filters (length ratio 0.5–2.0, no empty outputs, language-ID check).

3. **Evening:** Start LoRA fine-tune on the 5K Hindi pairs. Training completes overnight (~17 min, but including eval sweeps: ~2h).

This gives us, by Day 2 morning, both a prompt-only baseline and a first SFT checkpoint to compare — the minimum information needed to decide whether SFT is viable before investing in all 6 languages.
